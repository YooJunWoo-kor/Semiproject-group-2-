* ERP 프로젝트 리팩토링 핵심 정리  
1. 전체 방향  
- 기존 yjw의 화면 디자인, 기능, 라우팅은 그대로 유지  
- 보이는 화면은 바꾸지 않고 내부 구조만 정리  
- 파일 역할을 분리해서 문제 발생 시 찾기 쉽게 구성  
- 나중에 DB 연결 시 화면 파일을 크게 수정하지 않도록 준비  
  
2. 기본 데이터 흐름  
현재:  
화면(Page) -> Service -> localStorage / 더미 데이터  
  
나중:  
화면(Page) -> Service -> API -> Node/Express -> MySQL  
  
핵심:  
화면이 데이터를 직접 관리하지 않고 Service를 통해 접근하도록 정리  
  
3. 역할별 파일 구조  
pages/  
- 실제 화면  
- 화면이 이상하면 가장 먼저 확인  
  
components/  
- 여러 곳에서 반복해서 사용하는 UI  
- 테이블, 카드, 폼 등  
- 무조건 잘게 쪼개지 않고 실제로 반복되는 경우만 분리  

services/  
- 데이터 조회, 저장, 로그인 판별 등  
- 현재는 localStorage/더미 데이터 사용  
- 나중에는 API 호출로 교체  
  
data/  
- MASTER 계정, 일반 직원 계정 등 현재 사용하는 더미 데이터  
- 화면 파일에 직접 데이터를 복붙하지 않도록 분리  
  
utils/  
- 공통 함수 또는 기존 코드와의 호환용 파일

## yjw 브랜치 주요 문제 해결 사례

### 1. 기안서 유형별 상세 데이터 저장 구조 개선
- **문제:** 휴가·구매·비용 기안서마다 추가 입력 항목이 달라 임시저장 후 수정·재조회까지 상세 데이터를 유지할 구조가 필요했음.
- **원인:** `my_draft`의 공통 컬럼만으로는 문서 유형별 입력값을 표현하기 어려웠고, 상세 데이터의 저장·조회 규칙도 일관되지 않았음.
- **해결:** `detail_data` JSON 컬럼을 도입하고 API 검증, INSERT·UPDATE·SELECT, 프론트엔드 JSON 파싱을 동일한 데이터 구조로 연결함.
- **결과:** 문서 유형별 추가 정보를 하나의 기안서 레코드에 저장하고 임시저장·수정·상신 흐름에서 다시 사용할 수 있도록 구현함.

### 2. 다중 결재 단계의 상태 일관성 확보
- **문제:** 기안서 본문과 결재자별 진행 단계가 별도 테이블에 저장되어 상신·승인 과정에서 두 데이터의 상태를 함께 관리해야 했음.
- **원인:** `my_draft`와 `draft_approval_steps`가 분리되어 있어 저장 작업 일부만 성공하면 문서 상태와 결재선이 불일치할 수 있었음.
- **해결:** 상신 시 두 테이블의 변경을 트랜잭션으로 처리하고 첫 결재자는 `PENDING`, 후속 결재자는 `WAITING`으로 등록했으며, 승인 시 `SELECT ... FOR UPDATE`로 현재 단계를 확인하고 다음 단계만 활성화함.
- **결과:** 현재 결재 순서에 해당하는 사용자만 처리할 수 있고, 마지막 승인 또는 반려 결과가 기안서 상태에 반영되는 순차 결재 흐름을 구현함.

### 3. 휴가 데이터 저장 기준 일원화
- **문제:** 휴가 신청 정보가 `my_draft`와 `draft_leave`로 나뉘어 기안서·휴가 목록·연차 집계·당일 휴가 확인의 데이터 기준이 달라질 수 있었음.
- **원인:** 동일한 휴가 기간을 별도 테이블과 기안서 상세 데이터에 중복 저장하고, 조회 로직도 서로 다른 테이블을 참조했음.
- **해결:** 휴가 기간을 `my_draft.detail_data` JSON에 저장하는 기준으로 정리하고, `JSON_EXTRACT`를 사용하도록 휴가 조회·연차 집계·당일 휴가 확인 SQL을 수정함.
- **결과:** 휴가 신청 원본과 관련 조회 로직이 `my_draft`를 기준으로 동작하도록 정리해 데이터 관리 경로를 단순화함.

### 4. 레거시 DB 스키마 호환성 개선
- **문제:** 팀 브랜치 병합 및 개발 환경별 DB 차이로 일부 선택 컬럼이 없는 경우 직원·부서 조회 API가 실패할 수 있었음.
- **원인:** `initial_annual_salary`, `resignation_date`, 계정 권한 및 부서장 관련 컬럼을 모든 DB에 존재한다고 가정하고 조회했음.
- **해결:** `information_schema.COLUMNS`에서 실제 컬럼을 확인한 뒤 존재하는 컬럼만 SELECT·JOIN에 반영하고, 누락된 선택 항목은 `NULL`로 반환하도록 동적 쿼리를 구성함.
- **결과:** 선택 컬럼이 일부 누락된 DB에서도 기본 직원·부서 조회가 가능하도록 하여 스키마 차이에 대한 호환성을 높임.

### 5. 대시보드 API 부분 실패 격리
- **문제:** 근태·부서·직원 요약을 함께 불러올 때 한 API의 실패로 다른 API의 정상 응답까지 화면에 반영되지 않는 문제가 있었음.
- **원인:** `Promise.all`은 요청 중 하나라도 실패하면 전체 결과 처리를 중단하는 구조였음.
- **해결:** `Promise.allSettled`로 요청별 성공·실패를 분리하고, 각 응답을 독립적으로 상태에 반영하며 영역별 오류 메시지를 관리하도록 변경함.
- **결과:** 특정 요약 API가 실패해도 나머지 정상 데이터는 대시보드에 표시되고, 실패한 영역만 별도로 안내하도록 개선함.
